# What the AI-Native Design Buys

This is the thesis of the prototype. It argues one claim: a conventional ALM system's model lives in a GUI, and this engine makes the same model legible and addressable to a language model instead. The argument is grounded in what shipped, not in what a demo could be made to look like. Every mechanism it names is in the repo with tests.

## The problem, stated precisely

In a typical desktop ALM system the entire domain model is a set of named database tables edited through a thick client. That is not a criticism of the schema, which is often good; it is a statement about where the model can be reached from. Three consequences follow, and they are the three this prototype answers.

First, the assumptions live in dialog boxes. Every run is assembled through a modal form and persisted as a saved run definition; there is no scripting API, no job DSL, no headless or CI invocation, and distributed compute is an add-on rather than a native capability. The run has no versioned artifact to target because the run is an act of clicking, not a document.

Second, the reasoning lives in the analyst's head. The system computes the numbers; the account of why a number moved is reconstructed afterward by the person who ran it, from a report they read. Nothing in the schema carries the decomposition.

Third, the audit trail is a screenshot. Setup tables often carry only a last-writer change stamp with an optional comment, and the change log is something a user can clear. Stochastic runs are not independently reproducible when exact replication depends on unchanged surrounding inputs rather than a stored seed-plus-input snapshot. For a model feeding IRRBB, EVE, and CECL-adjacent numbers under SR 11-7-style expectations, that is the single most disqualifying gap.

"AI-native" is the answer to those three, and it is a structural answer, not a chat box bolted onto a report. Making the model addressable to a language model means the assumptions become typed objects a model can author and diff, the reasoning becomes a decomposition the engine computes and a model narrates, and the audit trail becomes a ledger that reproduces any number bit-for-bit. The six mechanisms below are how that was built.

## The six mechanisms, as built

**A typed tool surface.** The engine's primary interface is `EngineTools` in `packages/engine/src/contracts/tools.ts`: six typed, side-effect-explicit functions, `loadPortfolio`, `defineScenario`, `bindAssumptions`, `run`, `queryResults`, `explain`. Side effects are stated per method: `run` caches its result by `runId` so `queryResults` and `explain` read the same computed object rather than recomputing, and it is otherwise pure given its request and the registered portfolio. This is not a convenience layer over a GUI; it is the interface, and both the React viewer and the MCP server are clients of it. Neither computes a number. The viewer renders `RunResult`; the server forwards to `EngineTools`. That is the inversion an API-first design asks for: a core with the GUI as one client, not the source of truth.

**An MCP server over that surface.** `packages/ai/src/mcp/server.ts` is a thin adapter that lists seven tools (the six `EngineTools` calls plus `compileAssumptions`) and dispatches each to the injected engine. It computes no balance-sheet number itself. The end-to-end path is real and tested in process: `integration.test.ts` stands up the server against an in-memory transport pair, connects an MCP client, and drives a full `compileAssumptions` then `run` then `queryResults` then `explain` cycle over the fixture book. The assertion that matters is that the structured payload the client receives for `run`, `queryResults`, and `explain` equals the payload a direct `EngineTools` call returns, field for field. The adapter adds nothing and subtracts nothing. Malformed input is rejected, not coerced: a `run` whose seed is a number instead of a string is refused at the boundary. This is the differentiator against any ALM system that has no automation surface at all. Claude Code, or any MCP client, drives the whole engine with no GUI in the path.

**Natural language to a typed assumption set.** "Run a +200 parallel with MMA betas 15 points higher and prepayments at half speed" has to become executable, and the division of labor in `packages/ai/src/compiler/compiler.ts` is the load-bearing decision of the whole design. The language model authors a candidate `AssumptionSet`, a serializable list of overlay bindings wrapping the exact parameter blocks the vendored kernel models consume. It never computes a number. The compiler owns only the deterministic remainder: validate the candidate, diff it against the base, write the show-before-run rationale. Validation is two gates that both run before the candidate is hashed or diffed, so the show-before-run surface never displays a set that would die at run time. The first gate cross-checks every binding's target family against the run's catalogue with the same exact-string membership test `resolveAssumptions` applies at run time, and throws `UnknownFamilyError` on a hallucinated or wrong-case family. A model that invents a product family fails on the show-before-run surface, not silently at run time and not by dropping an unmatched security with no error at all. The second gate fills the content hash and rejects a malformed set. The compiled object, typed and hashed and diffed, is shown before it runs. A language model that did arithmetic on a balance sheet would be a liability; the contract makes that impossible, because the compiler's output type is data and only `run()` produces numbers.

**A provenance ledger.** Every run emits one `ProvenanceRecord` (`packages/engine/src/contracts/provenance.ts`): the hash over the full serialized input snapshot (portfolio, scenarios, assumption sets, grid, seed, market snapshot) excluding timestamps, the seed, the assumption-set ids with their content hashes, the kernel provenance reference (source commit plus the digest of the per-file hash manifest in `packages/kernel/PROVENANCE.md`), the named model versions in sorted-key order, and the two wall-clock timestamps injected from outside the compute path. The last point is what lets the core stay deterministic while the ledger still records when the run happened. Two runs with the same inputs hash and seed produce byte-identical results; this was verified across separate processes, identical modulo the two injected timestamps. This is the SR 11-7 governance surface a GUI-bound system rarely offers: it replaces a flat simulation log, a last-writer stamp, and a "replicate soon after" caveat with an artifact a model risk function can actually ask for.

**An explain layer that narrates and declines.** "Why did EVE fall in +200?" is answered only from the `AttributionResult` the engine computed, never from a language model's impression of the report. The engine decomposes each headline delta into per-family, per-driver contributions and carries the unexplained residual explicitly, defined as `sum(contributions) - totalDelta` and never folded into a driver (`results.ts`). In a regulatory grid every shocked scenario shares the base assumption set and new-business strategy, so the rate driver carries the whole family delta and the decomposition is exact, residual at float noise near 1e-9 (`run/attribution.ts`). The honesty is in what it refuses. A scenario that also changes assumptions or new business is a genuine multi-driver decomposition whose intermediate peel states this prototype does not build; rather than fabricate a split, its headlines are declined with a `NotImplemented` tag and the rest of the run proceeds. The narration layer (`packages/ai/src/explain/compose.ts`) reads attribution figures verbatim and computes nothing, a property enforced by a source scan that fails the build if any arithmetic operator survives in its executable code. When the decomposition cannot support the question, the `Explanation` carries `supported: false` and the prose says the attribution cannot support a driver-level answer. The model narrates a decomposition it was handed; it does not form a view of its own.

**Structured everything.** Every number lives in a typed shape and serializes to JSON with a stable schema (`results.ts`, `run.ts`): a `schemaVersion` on the envelope, additive evolution, no `NaN` or `Infinity` in serialized output, and collections held as arrays in a declared order rather than Maps so serialization never depends on iteration order. No number exists only as a rendered pixel. In a typical desktop ALM system, Excel is the type system, the reporting engine, and the archive at once; the answer is that the typed result is the substrate and Excel or BI would be an export target, not the store.

## The honest boundaries, as part of the thesis

These belong in the argument, not in an appendix, because the division of labor is the argument.

The natural-language author is a live-model seam without automated coverage. The compiler injects the authoring step as a `CandidateAuthor` so the deterministic pipeline is testable against a fixed instruction-to-candidate map; production passes the Claude-backed author. Everything downstream of the candidate is tested and deterministic, and the family gate and the validator catch a malformed or hallucinated candidate. What is not covered by an automated test is the quality of the live model's authoring itself: whether the model turns "half speed" into the right parameter change. That is a real gap, and the mitigation is architectural rather than statistical. The candidate is untrusted data, gated and diffed and shown before it runs, so the failure mode is a visible wrong diff on the show-before-run surface, not a silent wrong number in a result.

The explain layer narrates only what attribution supports. The rate-only peel is exact; the multi-driver peel is declined, not approximated. An answer the attribution cannot ground is refused rather than manufactured. This is a smaller scope than "the model can explain anything," and that is the point: the smaller scope is the honest one.

A language model doing arithmetic on a balance sheet would be a liability. This is why the labor is split the way it is, and why the split is enforced in types rather than in a prompt. The model authors objects and narrates decompositions; the engine computes every number; the boundary is a compile error to cross, not a convention to remember.

## What this buys a model risk function, concretely

Three capabilities that a GUI-bound design cannot offer, each of them shipped and tested.

Reproduce any number from the ledger. Given a `ProvenanceRecord`, the inputs hash plus the seed reconstruct the run bit-for-bit, timestamps excepted. A validator does not have to trust the analyst's memory of what was run; the run is a document, and the document reproduces the number.

Diff any two assumption sets. Two sets diff field by field into a typed `AssumptionDiff`, which is what the show-before-run step renders and what a challenge function reads to see exactly what a stress changed. There is no equivalent to reading two screenshots of two dialog boxes.

Drive the whole engine headless. The MCP server exposes the full surface with no GUI in the path, and the 100k-position synthetic book runs end to end this way in about 110 seconds. Batch, CI, scheduled runs, and a model-driven client are all the same interface, because the interface is the engine and the GUI was never the source of truth.
